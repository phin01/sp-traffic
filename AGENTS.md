## Quick start
- Copy `.env.example` → `.env` and fill in credentials (DB, Azure, SPTrans token).
- Use the project's virtual environment (`.venv`).
- All scripts run as modules from the project root:  
  `python -m ingestion.olho_vivo.linhas_staging.main`

## Key conventions
- **Env loading**: Always `load_dotenv(dotenv_path=find_dotenv())` from `dotenv`.
- **Cloud storage**: Use `utils.cloud.CloudStorage` for all blob operations. Never import Azure clients directly.
- **Relative paths**: When referencing files (data, configs), use paths relative to the project root.
- **Sandbox**: Any test/exploratory script goes in `/sandbox`. Name it descriptively.
- **No new packages**: Only packages in `requirements.txt` are allowed.

## Architecture in one line
Olho Vivo/Open Meteo APIs → Python ingestion → JSON blobs in Azure → PostgreSQL staging tables → dbt transformation (WIP).

## Running dbt
- dbt project lives in `/transformation`.
- From that directory: `dbt run`, `dbt test`, etc.
- Profiles are in `transformation/profiles.yml`.
- Note: dbt credentials are hardcoded in `profiles.yml` (different from `.env`).

## Common pitfalls
- Olho Vivo API requires cookie‑based auth: always use a `requests.Session` and call `Login/Autenticar?token=...` first.
- Weather queries are grid‑based: stops are grouped into ~64 cells (0.025°) to reduce API calls. See `CONTEXT.md` for grid dimensions.
- The logger (`utils.logging.get_logger`) writes run metadata to `logging.script_runs`; don’t instantiate your own DB connection for logging.
- Raw API responses are stored as‑is in Azure; transformations happen later in dbt.
